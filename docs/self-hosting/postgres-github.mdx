## Postgres instead of files

By default the central server keeps its tokens and sandboxes in files under `/var/lib/ephemera/server`. That's all one machine needs. To keep them in Postgres instead, which also keeps a history of finished sandboxes, set the database's URL in `/etc/ephemera/ephemera.env` and restart the server:

```bash
EPHEMERA_DATABASE_URL=postgres://ephemera:PASSWORD@db.internal:5432/ephemera
```

The server creates its tables on first start and updates them on upgrades. `ephemera-server token` commands use the database when `EPHEMERA_DATABASE_URL` is set, so run them with it:

```bash
sudo --preserve-env=EPHEMERA_DATABASE_URL ephemera-server token ls
```

or pass `--database URL`. Tokens in the files are not copied over; make new ones.

In Postgres, token names are unique within an account rather than across them. When two accounts have a token with the same name, revoke or change it by its id.

<Note>
  Use a direct connection, not a transaction-mode pooler such as a `-pooler` endpoint: the server takes a lock while it updates its tables.
</Note>

## Sign in with GitHub

With Postgres, people can also sign in with GitHub and make their own tokens, each in an account of their own.

<Steps>
  <Step title="Make a GitHub OAuth app">
    On GitHub: Settings, Developer settings, OAuth Apps, New OAuth App. Set the callback URL to `https://<your server>/auth/github/callback`.
  </Step>
  <Step title="Configure the server">
    Add to `/etc/ephemera/ephemera.env`:

    ```bash
    EPHEMERA_GITHUB_CLIENT_ID=...
    EPHEMERA_GITHUB_CLIENT_SECRET=...
    EPHEMERA_PUBLIC_URL=https://ephemera.example.com
    EPHEMERA_DASHBOARD_URL=https://ephemera.example.com/dashboard
    ```

    `EPHEMERA_PUBLIC_URL` is where browsers reach the server. `EPHEMERA_DASHBOARD_URL` is where people land after signing in; pages from its origin may call the API with the session cookie.

    The dashboard is the Next.js app in the repository's `site/` folder. Build it with `NEXT_PUBLIC_EPHEMERA_API` set to your server's public URL, and serve it at the dashboard URL's site.
  </Step>
  <Step title="Put HTTPS in front">
    The server has no HTTPS of its own yet, so put it behind a proxy that has it, and use `https://` in both URLs. Browsers only send the session cookie over HTTPS.
  </Step>
</Steps>

With sign-in on, `ephemera login` in a terminal signs a machine in through the browser. It shows a code like `K7QM-2XRT` and opens the dashboard's `/device` page, where the person checks the code and approves. The CLI then gets a device token named after the machine, listed under the account's tokens. The code works for 10 minutes, and its token can be collected once; the server makes the token only then, so it never stores it in the clear. `ephemera login --with-token`, or piping a token in, still works, for CI.

## What sign-in keeps

Sign-in asks GitHub only for `read:user`: the person's id, login, name and avatar, never their repositories. GitHub's access token is used once to read those and isn't kept. A GitHub user's account is `gh-` and their GitHub user id, so renaming their login changes nothing.

Sessions last 30 days and live in an `HttpOnly` cookie; only a hash of each is stored. Requests that change something with a session must come from the dashboard's own site. A session can read and stop the account's sandboxes and remove its hosts, but it can't make sandboxes: only the CLI can, since only the CLI holds a sandbox's token.
